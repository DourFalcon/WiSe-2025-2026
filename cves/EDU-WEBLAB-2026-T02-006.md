Vulnerability Report
 
  CVE-ID: EDU-WEBLAB-2026-TEAM2-006
 
  Title:   GraphQL API Allows Unauthorized Execution of Queries and Mutations Leading to Full Data Exposure and Privilege Escalation
 
  Affected Lab:   graphql-galaxy
 
  Component:   GraphQL API Endpoint — Query and Mutation Execution Interface
 
  Severity:   Critical
 
  CVSS Vector:   CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N
 
  CVSS Score:   9.1
 
  Description:  
A critical authorization vulnerability was identified in the GraphQL API of the graphql-galaxy machine, where the application exposes a fully functional GraphQL console without enforcing any authentication or authorization controls on query and mutation execution. The root cause lies in the absence of access controls on the GraphQL schema, combined with an enabled introspection endpoint that allows unauthenticated clients to enumerate all available types, queries, and mutations supported by the API. An attacker can leverage Burp Suite's built-in GraphQL scanner to automatically generate valid queries from a captured request, then execute those queries without providing any credentials to enumerate all registered users and retrieve sensitive administrative account details. This was demonstrated by successfully listing all users in the system and querying admin-level account data, which exposed the flag — confirming complete unauthorized access to privileged information. The ability to execute unrestricted mutations further amplifies this risk by allowing an unauthenticated attacker to create, modify, or delete user records, constituting a critical breach of both confidentiality and integrity.
 
  Proof of Concept:    graphql
  
  Introspection query used to enumerate the full schema:
{
  __schema {
    types {
      name
      fields {
        name
        type {
          name
        }
      }
    }
  }
}
 
Query used to list all registered users:
{
  users {
    id
    username
    email
    role
  }
}
 
Query used to retrieve admin account details (flag exposed in response):
{
  user(id: 1) {
    id
    username
    email
    password
    flag
  }
}
 
 Mutation used to create an unauthorized user account:
mutation {
  createUser(username: "attacker", email: "attacker@evil.com", password: "pwned123", role: "admin") {
    id
    username
    role
  }
}

 
  Steps to Reproduce:  
1. Navigate to the graphql-galaxy machine's web interface and click   "Enter GraphQL Console"   to open the interactive query interface.
2. Observe that the GraphQL console loads without requiring any login, registration, or API token — confirming there is no authentication gate on the endpoint.
3. Open Burp Suite and configure your browser to proxy traffic through it; reload the GraphQL console page to capture the initial HTTP request to the GraphQL API endpoint.
4. In Burp Suite, right-click the captured request and select the   GraphQL scanner   option to automatically generate a list of valid queries and mutations derived from the API's introspection response.
5. Observe that the scanner successfully enumerates multiple queries and mutations, confirming that introspection is enabled and the full schema is publicly accessible without authentication.
6. Send the `users` query (generated by the scanner) to list all registered user accounts, and confirm that a full user list including usernames, emails, and roles is returned in the response without any credential requirement.
7. Send the targeted `user(id: 1)` query to retrieve detailed information about the admin account, and verify that sensitive fields — including the flag — are disclosed in the response.
8. Execute the `createUser` mutation with attacker-controlled parameters and confirm that a new user account is successfully created, demonstrating that write operations are equally unrestricted.
9. Confirm the complete scope of impact: unauthenticated enumeration of all users, read access to privileged admin data, and the ability to perform unauthorized data modifications via mutations.
 
  Remediation:  
1.   Disable GraphQL introspection in all production and staging environments   — introspection should only be enabled in controlled local development environments, as it acts as a self-documenting attack surface; configure the GraphQL server (e.g., Apollo, Graphene) to reject introspection queries by default.
2.   Enforce authentication on all GraphQL operations   — require a valid session token or JWT Bearer token on every request to the GraphQL endpoint, and reject any unauthenticated request at the middleware level before it reaches resolver logic.
3.   Implement field-level and resolver-level authorization   — do not rely solely on endpoint authentication; every individual resolver must verify that the authenticated user has the appropriate role or permission to access the requested type or field (e.g., only `ADMIN` roles can query `password` or `flag` fields).
4.   Apply schema allow-listing (query whitelisting)   — restrict the API to only accept a predefined set of approved, hardcoded queries and mutations; reject any query that does not match the allow-list, preventing automated schema discovery and arbitrary query construction.
5.   Implement query depth and complexity limiting   — configure maximum query depth and complexity thresholds to prevent deeply nested or computationally expensive queries that could be used for data harvesting or denial of service.
6.   Apply the principle of least privilege to all GraphQL resolvers   — ensure sensitive fields such as passwords, flags, and internal identifiers are never exposed in the schema to roles that do not require them; use schema directives (e.g., `@auth`, `@hasRole`) to enforce access control declaratively.
7.   Enable comprehensive logging and anomaly detection on the GraphQL endpoint   — log all queries and mutations with the authenticated user identity, source IP, and response size; alert on patterns indicative of schema enumeration, bulk data retrieval, or unauthorized mutation attempts.
8.   Conduct regular GraphQL-specific security assessments   — include GraphQL endpoints in penetration testing scopes, specifically testing for introspection abuse, IDOR in resolver arguments, batch query attacks, and authorization bypass across all roles.
